# 结果解读与成绩提交

本文说明如何检查 native 评测结果并准备成绩材料。评测环境与实验记录要求见[复现说明](REPRODUCIBILITY.md)，运行问题见[故障排查](TROUBLESHOOTING.md)。

## 1. 运行产物

每次 native 评测会保存运行结果、候选记录和采集数据，主要包括：

| 文件或目录 | 内容 |
|---|---|
| `result.json` | 运行状态、基线、搜索最优记录和最终复测结果 |
| `metrics.json` | 加速比、STS 及指标可用性说明 |
| `solutions.json`、`evaluations.jsonl` | 各次评测记录 |
| `evaluations/` | 编译与测试日志、profiling 数据及单次评测结果 |
| `snapshots/` | 候选源码快照 |
| `usage.json` | token 使用量及相关计数证据 |

失败或提前中断的运行可能缺少部分产物，应保留已有记录并说明原因。bare 完整 harness 暂未开放，当前公开使用路径以 native 为准。

## 2. 结果检查

提交前请确认：

1. 任务和用例范围正确，冻结测试、golden 与数值容差未被修改。
2. 基线与候选均有完整的精度检查记录，并能对应到实际源码和 profiling 数据。
3. 已检查全部测试轮次、错误日志和最终复测结果；未执行复测时如实说明。
4. 失败、中断和缺失任务已列出，不只保留最好一次。

运行成功不等于性能提高；编译成功或单个通过标志也不足以证明全部测试通过。报告加速比时，应说明采用搜索最优结果还是最终复测结果，并保持环境和统计口径一致。

## 3. 指标口径

STS 以 native 的 **`linear-budget-delay-v1`** 为准，使用原始 `metrics.json`，不以其他汇总脚本的同名分数覆盖。公式及计分窗口见[指标说明](../eval/native_harness/core/references/metrics_master.md)。

STS 衡量固定预算内的搜索改进，最终复测不参与搜索计分。`raw_speedup` 可以包含预算窗口外的通过候选，因此可能与 STS 窗口内的最佳加速比不同；token 与时间指标应分别报告。

不可用或缺失的指标保留原状态和原因，不补成 0，也不用估算 token 或假设参数填补证据。异常结束的部分观测不能视作完整运行结果。本地结果仍需经项目团队审核后才能作为正式成绩发布。

## 4. 提交材料

建议按实验批次整理以下材料：

- **实验信息**：机构与联系人、代码和数据版本、harness、agent、模型、任务覆盖范围、运行预算及独立运行次数。
- **环境信息**：NPU 型号、驱动与工具链版本、镜像引用或自建环境说明、profiling 采样协议。建议使用 Ascend 910C，并尽量覆盖全部 17 个任务。
- **评测产物**：第 1 节列出的原始结果、日志、源码快照、usage 和 profiling 数据，保持各次评测之间的对应关系。
- **结果说明**：精度与性能结论、失败或缺失项；如附汇总文件，注明其来源和生成方式。

分享前制作脱敏副本，移除密钥、带凭据的地址及无关私有信息，保留内部原始记录。profiling ZIP 与解压目录通常无需重复提供；没有采集数据的失败评测仍应保留错误记录。

## 5. 提交方式

请通过 [Leaderboard Import 页面](https://slai-aitp.github.io/AscendGYM/#/imports)查看联系方式，当前网页入口显示联系弹窗，不会自动上传成绩文件。

目前不设固定的材料大小上限。建议整理完整后按批次提交，避免频繁重复上传；更正或补充时说明变化。

# 评测复现与结果可比性

本文说明实验记录与结果比较的基本要求。建议使用 Ascend 910C NPU 采集 profiling，尽量覆盖 Batch 1 的全部 17 个任务。

## 1. 固定实验身份

建议保存以下信息，未知项如实标注，分享前移除认证信息：

| 项目 | 记录内容 |
|---|---|
| 代码与数据 | 仓库提交、未提交修改、任务 ID、数据版本及实际用例范围 |
| Harness、模型与 agent | harness、实际模型标识、服务协议、agent CLI 版本、配置和提示模板 |
| 预算 | 候选评测上限、STS 计分窗口、最终复测次数 |
| 环境 | 镜像引用或自建环境版本、NPU、驱动、CANN、Python、torch/torch_npu 及构建依赖版本 |
| 采样协议 | 总轮数、预热轮数、统计方法和 profiler 版本 |
| 运行过程 | run ID、启动命令、起止时间、资源共享情况、中断与人工干预 |

## 2. 启动前检查

1. 固定代码和数据快照，保存本地修改与配置。
2. 确认原始基线通过全部冻结用例；调试子集单独标记。
3. 核对服务地址和实际执行环境，通过无模型联调验证编译、测试与 profiling。
4. 明确本次模型、预算和复测设置，记录设备共享情况。

启动方法见[根 README](../README.md#quick-start)，联调与日志检查见[故障排查](TROUBLESHOOTING.md)。

## 3. 保持任务与采样协议一致

冻结测试、golden、输入和数值容差不由优化 agent 修改，候选仅修改任务允许的源码路径。任务本身的修正应作为数据集版本变更处理，并说明对历史结果的影响。

native 的 `--profiling-runs` 表示测量轮数，`--warmup-runs` 表示额外预热轮数。核对实际完成的轮次与统计方式；比较结果时保持任务、用例、硬件、软件和采样协议一致。不同环境的绝对耗时不能直接比较，加速比也不能消除全部测量差异。

## 4. 区分搜索、复测和独立运行

- **搜索**：保留通过、失败和无改进的候选及源码快照。候选次数上限与 STS 计分窗口分别记录。
- **最终复测**：对选定版本重复评测，保留次数、逐次结果和源码版本；未执行时明确说明。
- **独立运行**：重新启动一次 agent 搜索。复制目录或对同一实现重复 profiling 不算独立搜索。

报告实际运行次数、结果选取和聚合方法，同时列出失败、中断和缺失项，不把最好一次称为平均表现。

## 5. 保留指标与原始证据

STS 采用 native 的 `linear-budget-delay-v1`，保留原始 `metrics.json`、预算窗口和计算版本，token 与时间指标分别报告。公式见[指标说明](../eval/native_harness/core/references/metrics_master.md)，结果解读见[结果说明](RESULTS_AND_SUBMISSION.md#3-指标口径)。

缺失或不可用指标保留原状态和原因，不补成 0，不估算候选完成 token，也不虚构 workload 或硬件参数。异常结束的部分观测应单独说明。

将实验与环境信息、配置、候选源码、原始结果、日志和 profiling 数据一并归档，保持结果与源码的对应关系。派生汇总注明来源与计算版本，不覆盖原始运行记录。提交材料与脱敏要求见[结果与提交说明](RESULTS_AND_SUBMISSION.md)。
